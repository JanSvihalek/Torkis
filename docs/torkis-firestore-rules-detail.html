Verze aplikace 5.1.8 · Stav k 4. 6. 2026 · Projekt visto-51cb7 · Ověřeno 32 automatickými testy

1. Princip: kde a kdy se pravidla vyhodnocují

Bezpečnostní pravidla Firestore jsou kód, který běží na serverech Google u každého přístupu k databázi. Nejsou součástí aplikace — proto je nelze obejít úpravou klienta nebo přímým připojením k databázi.

Obr. 1 — Každý požadavek projde přes server: nejdřív identita (Auth), pak autorizace (pravidla), teprve pak data.

Tři základní zásady našich pravidel:

  • Vše zakázáno, dokud to pravidlo výslovně nepovolí (deny by default).
  • Izolace servisů — každý vidí jen data svého servis_id.
  • Čtení = jednotlivý dokument (get) i dotaz (list) — u dotazu navíc platí zvláštní podmínka (viz kap. 5).

2. Pomocné funkce

Pravidla stojí na několika funkcích, které se volají opakovaně:

FunkceVrací true, když…

Klíčová funkce ownsServis() — anotovaný kód

// Patří daný servis_id přihlášenému uživateli?
function ownsServis(sid) {
  return signedIn() && (
    sid == request.auth.uid                 // (A) bootstrap / vlastní servis
    || (exists(/.../uzivatele/$(request.auth.uid))  // (B) profil existuje
        && myServisId() == sid)             //     a jeho servis_id sedí
  );
}
Obr. 2 — Rozhodování ownsServis(). Větev (A) je důležitá pro onboarding (profil ještě neexistuje), větev (B) pro zaměstnance.

5. Dotazy (list) — proč musí klient filtrovat

U dotazu, který vrací více dokumentů, pravidla nefiltrují výsledek — buď celý dotaz povolí, nebo odmítnou. Firestore povolí dotaz jen tehdy, je-li zaručeno, že vrátí pouze dokumenty splňující pravidlo. Proto musí klient sám přidat filtr where('servis_id' == můj servis) — jinak je dotaz zamítnut.

Obr. 4 — Aplikace TORKIS u všech seznamů filtruje podle servis_id, takže dotazy projdou; útočníkův „dej mi vše“ dotaz server odmítne.

6. Onboarding — proč existuje větev „sid == uid“

Při prvním nastavení se v jednom dávkovém zápisu zakládá profil uživatele i nastavení servisu, úkony a trial. V té chvíli ale profil uzivatele ještě není uložen, takže by se z něj nedalo přečíst servis_id. Řeší to větev (A) v ownsServis(): zakladatel zakládá svůj servis pod vlastním uid (servis_id == uid), což pravidlo pustí i bez existujícího profilu.

Obr. 5 — Bootstrap onboardingu: jeden dávkový zápis, povolený díky shodě servis_id s uid zakladatele.

9. Serverové kolekce a „vše ostatní zakázáno“

Kolekce, které drží limity placených funkcí — počítadlo využití (pouziti) a cache (vin_cache, value_cache) — klient nesmí číst ani zapisovat. Mění je jen backend (Cloud Functions přes Admin SDK, který pravidla obchází, ale je dostupný jen serveru). Cokoli, co není ve výše uvedených pravidlech, je ve výchozím stavu zamítnuto — nová kolekce tedy není omylem otevřená.

10. Ověřování pravidel (testy)

Pravidla jsou pokryta 32 automatickými testy v lokálním Firestore emulátoru (izolace servisů, dotazy, onboarding, eskalace, serverové kolekce, portál). Postup při změně: upravit pravidla → spustit testy v emulátoru → teprve pak nasadit (firebase deploy --only firestore:rules). Testy jsou ve složce tools/rules_test/.

Shrnutí: Pravidla běží na serveru, ve výchozím stavu vše zakazují a otevírají přístup výhradně členům správného servisu. Onboarding je ošetřen speciální bootstrap větví, samostatně je ošetřena správa uživatelů (s blokem eskalace práv), zákaznický portál i serverové kolekce. Vše je ověřeno automatickými testy.
